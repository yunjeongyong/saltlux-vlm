# LUXIA VLM — 문서·영수증 파싱 모델 개발

**기간** 2026-08 ~ 진행중 · **소속** 솔트룩스 · **유형** 사내 프로젝트 (삼성SDS 협업 과제)
**역할** 학습 데이터 구축 · 파인튜닝 · 성능 평가
**기술** VLM, PyTorch, LoRA, FSDP, Python, H100 ×8

---

## 프로젝트 개요

영수증·문서 이미지를 구조화된 텍스트(마크다운 본문 + HTML 표)로 변환하는 VLM을 개발한다.
Qwen3.6-35B-A3B를 베이스로 LoRA 파인튜닝하며, 데이터 설계부터 학습·평가까지 담당한다.

문서 파싱은 일반 이미지 인식과 성격이 다르다. 촬영 각도·조명에 따른 품질 편차, 발행처마다
다른 레이아웃, 그리고 **같은 항목을 어디까지 하나의 필드로 볼 것인가**라는 정의의 모호함이
성능을 좌우한다. 모델 구조보다 데이터의 정의·품질과 그것을 검증할 측정 체계가 결정적이라고
보고 일한다.

| | 규모 |
|---|---|
| 학습셋 | 4,496 → 11,173 → 50,457 → 48,400행 (7차 실험) |
| 평가셋 | 블록 크롭 1,019건 (텍스트 921 / 표 98), 영수증 92장에서 추출 |
| 자체 생성 데이터 | 합성 영수증 3,000장 + 파생 크롭 12,000장 |
| 학습 환경 | H100 80GB × 8, LoRA r=16 (학습 파라미터 49.8M / 35.16B) |

## 1. 합성 영수증 생성기 — 라벨이 확정적인 데이터를 만들었다

**문제.** 실물 영수증이 95장뿐이었다. 학습용 크롭이 913개 중 892개(97.7%)까지 소진되어
재료가 바닥났고, 사람 라벨링을 늘리는 것은 비용과 시간이 맞지 않았다.

**접근.** 영수증을 렌더링하는 생성기를 직접 만들었다. 핵심은 **라벨을 렌더링 좌표에서
기하 변환으로 얻는 구조**로 설계한 것이다. 회전·원근·말림을 적용해도 좌표가 정확히 따라오므로
어절·줄·블록·표셀 4단계 bbox와 정답 텍스트가 **사람 손을 거치지 않고 확정된다.**

- v1 스캔풍 1,000장 — 넓은 형태, 흰 종이, 책상 배경
- v2 촬영풍 1,000장 — 좁고 긴 감열지, 바코드, 손에 든 각도, 손가락 가림
- 파생 크롭 12,000장

**검증.** 2,000장 전수 검사에서 공급가액+부가세=합계 불일치 0건, 품목합=합계 불일치 0건,
bbox 이탈 0건.

**놓칠 뻔한 것.** 촬영풍의 손가락 가림 798장 중 **172장에서 손가락이 어절을 90% 이상 덮고
있었다.** 정답에는 있는데 이미지에는 안 보이는 텍스트라 모델에 환각을 가르치는 데이터였다.
좌표 겹침을 계산해 걸러내고 학습셋에서 1,204행을 제외했다. 종이 가장자리만 가리는 것은
실제 촬영과 같은 조건이라 남겼다.

## 2. 데이터를 5배 늘렸는데 성능이 오르지 않았다 — 원인은 정답 오염

![실험별 성능](images/01_experiment_metrics.png)

**증상.** 학습셋을 11,173행에서 50,457행으로 늘렸는데 지표가 오르지 않았다.
텍스트 완전일치율 64.4%는 5배 적은 데이터로 학습한 exp_004(64.2%)와 같았고,
표 TEDS와 종합 지표는 오히려 떨어졌다.

**추적.** 모델 출력을 직접 열어봤다. 텍스트 크롭인데 `<td>1,000</td>` 처럼 **표 태그를 붙여
답하고** 있었다. 정답이 `합계` 두 글자인 크롭에도 같은 형태로 나왔다.

학습 정답을 역추적한 결과가 이것이다.

![오염률](images/04_label_contamination.png)

외부 후보 데이터를 편입할 때 **표에서 떼어낸 크롭의 셀 태그를 벗기지 않아** 정답
1,757건(4.9%)이 오염돼 있었다. 기존 학습셋(exp004c)에는 0건이었다. 출처별로 보면
crawl 47.1%, korie 12.0%로 특정 소스에 몰려 있었다.

**모델이 지어낸 게 아니라 배운 대로 한 것이었다.**

**조치.** 태그 제거 904행, 정답이 비어 있던 행(`<tr>` 만 있는 행) 853행 삭제. 정제본으로
재학습을 진행 중이다. 더 중요한 것은 원인이 **데이터를 늘리는 절차에 정답 형식 검증이
빠져 있었다**는 점이라, 편입 파이프라인 앞단에 태스크별 검사(텍스트 태스크에 HTML 금지,
빈 타깃 금지)를 넣는 것을 제안했다.

## 3. 평가 지표가 모델을 잘못 판정하고 있었다

**증상.** 평균 CER이 1.93으로 나왔다. 문자 오류율이 1을 넘는다는 건 정답보다 긴 오답을
쏟아낸다는 뜻이라, 모델이 망가진 것처럼 보였다.

**추적.** 분포를 뜯어보니 **중앙값은 0.0000**이었다. 텍스트 921건 중 26건(2.8%)이 평균을
전부 끌어올리고 있었다.

```
GT:   '합계'                                    2자
PRED: '000000000000000000000000...'         1,024자 = 생성 상한
→ CER 512
```

같은 20자 조각이 1,003회 반복된 **생성 반복 루프**였다. 폭주 26건 중 14건이 GT 10자 이하의
짧은 크롭이었고, 크기를 재보니 정상 크롭보다 5배 넓은 형태였다 — 표의 한 행처럼 보이는데
정답은 두 글자인 크롭이다.

**처방.** 학습 없이 디코딩 설정만으로 잡히는지 검증했다.

![폭주 억제](images/02_runaway_suppression.png)

**부작용 검증을 같이 설계했다.** 반복 억제는 `10,000` 같은 숫자나 반복되는 품목 줄처럼
원래 반복이 정답인 텍스트를 망가뜨릴 수 있다. 그래서 폭주군 35건과 함께 **정상 대조군 40건**
(어느 모델에서도 완전일치였던 크롭)을 같이 측정했다. 네 설정 모두 대조군 완전일치 40/40을
유지했고, `repetition_penalty` 만 1건을 망가뜨려 탈락했다.

전량 921건 환산 시 **평균 CER 1.9313 → 0.1519**. 학습 없이 40분이었다.

다만 표 크롭은 아직 검증하지 않았다. HTML 표는 `</td><td>` 가 반복되는 구조라 같은 설정이
TEDS를 무너뜨릴 수 있어, 서빙 반영 전 확인이 필요하다고 기록했다.

## 4. 측정 단위를 다시 설계했다

문서 전체 정확도 하나로는 개선 방향이 안 잡힌다. 평가를 **블록 크롭 단위 1,019건**으로 쪼개고
텍스트는 CER, 표는 TEDS로 나눠 재도록 했다.

실제로 온라인 증강 실험(exp_005)에서 **텍스트 완전일치율은 오르고(64.2% → 65.3%) 표 구조는
떨어지는(0.7079 → 0.6831)** 상반된 결과가 나왔다. 회전·원근 증강이 글자 인식은 단단하게
만들었지만 표의 행렬 정렬을 흐트러뜨린 것으로 보인다. 통합 지표만 봤다면 "차이 없음"으로
묻혔을 내용이다.

**주지표도 바꿨다.** 평균 CER은 소수 폭주 건에 좌우되어 대표값으로 쓸 수 없다. 완전일치율,
CER 중앙값, TEDS, 폭주율(CER>1 비율)로 판정하도록 정리했다.

**측정의 함정도 기록했다.** eval_loss는 실험 간 비교가 성립하지 않는다 — 학습셋 토큰
중앙값이 510인데 검증셋은 1,331이라, 학습셋 구성을 바꾸면 eval_loss가 함께 움직인다.
모델 저하로 오독하기 쉬운 지점이다.

## 5. 학습 인프라 — GPU 8장 중 1장만 쓰고 있었다

![처리량](images/03_training_throughput.png)

**증상.** H100 8장으로 돌리는데 GPU 사용률이 1~12%였다. `device_map="auto"`가 데이터 병렬이
아니라 **파이프라인 병렬**이라, 35B 모델을 레이어 단위로 쪼개 얹고 한 번에 한 장만 계산하고
있었다. 4개 실험이 전부 이 상태로 돌았다.

**FSDP 전환.** 이전에 두 차례 실패한 이력이 있었다. 원인을 하나씩 규명했다.

1. **dtype 불일치** — FSDP는 파라미터 dtype이 균일해야 하는데, Trainer의 bf16 혼합정밀도가
   fp32 마스터 사본을 만들어 조건을 깬다. 모델과 LoRA를 처음부터 bf16으로 두고 Trainer의
   혼합정밀도를 끄는 옵션(`--pure-bf16`)을 추가해 해결.
2. **활성값 메모리** — 그 관문을 넘긴 뒤 24스텝에서 OOM. 가중치가 장당 8.2GiB로 줄어
   여유가 70GiB나 되지만 활성값을 전부 보관하면 그마저 찬다. gradient checkpointing을 켜서 해결.

**결과.** 13.43 → 6.38 s/it, **처리량 2.25배.** GPU 8장이 95~100%로 가동한다.
실험 한 번이 이틀에서 반나절로 줄었다.

중간에 DDP도 시도했으나 가중치 65.5GiB를 랭크마다 통째로 들어야 해서 **0.3GB 차이로 OOM**
났다. 스모크 20스텝은 통과했는데 본학습에서 죽었고, 원인은 스모크가 짧은 시퀀스만 만났기
때문이었다. **검증 설계가 부실하면 통과해도 의미가 없다**는 것을 기록으로 남겼다.

## 정리

이 프로젝트에서 성능을 움직인 것은 모델 구조가 아니었다.

- **데이터를 5배 늘려도 정답이 오염돼 있으면 효과가 없다.** 양을 늘리는 절차에 품질 검증이
  없었던 것이 실제 원인이었다.
- **지표가 이상하면 모델보다 측정을 먼저 의심해야 한다.** 평균 CER 1.93은 모델의 문제가
  아니라 2.8%의 폭주 건이 만든 착시였고, 중앙값은 0이었다.
- **통합 지표 하나로는 개선 방향이 안 잡힌다.** 텍스트와 표를 나눠 재고 나서야 증강이 한쪽만
  올린다는 것이 보였다.
- **검증 설계가 부실하면 통과해도 의미가 없다.** 짧은 시퀀스만 본 스모크는 본학습을 보증하지
  못했다.

문서 파싱에서 정의를 정확히 세우고 그것을 검증할 수 있는 측정 체계를 갖추는 일이 성능 개선의
출발점이라고 본다.
